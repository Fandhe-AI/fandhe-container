# コメント規約

## 目的

後続の読み手（Claude を含む）は渡された情報からしか判断できない。
コメントは crate・モジュール視点での役割と、他 crate・plugin・カーネル / OS API との
文脈を埋め込み、ファイル単体で文脈が伝わる状態にする（AI 自己補修の前提。REPAIR 系ビヘイビア）。

## 何を書くか

- このファイル・モジュール・関数の役割と責務境界（1〜2 行要約をドキュメンテーションコメントで）
- 呼び出し元・呼び出し先の文脈（「supervisor の restart ループから呼ばれる」「`fandhe-container-plugin`（境界機構）のフレームを復号して `ContainerRuntime` へ渡す」等）
- 他 crate・plugin との契約（公開トレイト・フレーム形式・エラー型・前提条件・スレッド安全性・ACK / FLUSH ACK の保証範囲）
- spec のビヘイビア対応（該当する場合は ビヘイビア ID・TASK-n を併記する。[spec-reference](./spec-reference.md)）
- 未実装・簡易実装箇所の将来仕様（スタブであることを明示し、目指す挙動とビヘイビア ID を書く。REPAIR-3）
- 非自明な前提・副作用・エラー処理の意図（外部入力の検証根拠・カーネル版数要件・OS / アーキテクチャ差異の吸収理由・特権操作の後始末）

## 何を書かないか

- コードを読めば分かる逐語説明（`i += 1;  // i をインクリメント` 等）
- 陳腐化しやすい実装詳細の重複（コードと 2 重に管理しない）
- spec 本文の長い引用（ID を示して spec を参照させる）

## ドキュメンテーションコメントの形式

- Rust: crate・モジュールの入口は `//!`、公開 API は `///` で 1〜2 行の役割要約を必ず付ける
- コメントは日本語で書く（[japanese-style](./japanese-style.md)）
- `unsafe` ブロックには `// SAFETY:` で理由と維持すべき不変条件を必ず明記する
