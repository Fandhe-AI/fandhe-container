# イメージ由来 rootfs の寿命と delete の扱い

`create_with_image` が core 自身で作って公開した rootfs について、所有者・消すタイミング・失敗時の扱いを決める記録（#2378・OCI-7・OCI-5・OCI-6・SEC-1・REPAIR-3 / 4 / 5）。実装は `crates/core`（`oci_runtime::delete`・`oci_runtime::image_rootfs`・`StateRecord::image_rootfs`）。

## 背景

PR #2353（#2342）で、展開器（`ImageRootfsUnpacker`）つきの `create_with_image` は core が bundle 配下に rootfs を作って展開・公開するようになった。一方 `delete` は bundle も rootfs も消さなかったため、core が作った rootfs が残り続け、同じ bundle での再度の `create_with_image` が `AlreadyExists` で止まっていた。

spec では、OCI-6 の delete が消すのは状態ファイルと cgroup、OCI-7 では参照の解除だけが定められており、rootfs の寿命はどちらにも書かれていない。本書は core の実装上の決定であり、spec（OCI-6 / OCI-7）へ追記するかどうかは spec リポ側の判断事項とする。

## 決定

| 論点 | 決定 |
| ---- | ---- |
| 所有者 | 展開器つきの `create_with_image` が作って公開した rootfs だけを core が所有する。所有の印は状態レコードの `imageRootfs`（bundle 相対の経路と作成時の実体の dev・ino。`ImageRootfsRecord`）。利用者が用意した rootfs（通常の `create`・展開器なしの `create_with_image`）は利用者のもので、core は消さない（runc と同じ） |
| 消すタイミング | `delete`（`delete_releasing_image_ref` から呼ばれる場合も含む）の中で、`StateStore::delete` が成功した後に消す。使うのは関数の先頭で読んだレコード（実際に消した revision のもの）に付いた記録 |
| 状態削除の後にする理由 | start は `BundleLock` と revision の予約より前に rootfs の fd を固定する。状態削除の前に消す順だと、Created のコンテナで start が rootfs を固定し、delete が消し、start が予約し、delete の状態削除が `FailedPrecondition` になる窓が残る。状態の削除が成功した後なら、そのコンテナへの start・restart（supervisor）・update は revision 照合つきの `StateStore::update` で `NotFound` になるので、使用中の rootfs を消す窓が無い（supervisor の更新も `UpdateStateRequest::new(status, expected_revision)` を経る） |
| 消し方（fail-closed） | 記録した bundle を開き（bundle 自体は作成時と同じく追従する）、中間要素はリンク非追従の fd 相対で辿り、末尾もリンク非追従で開く。`fstat` の (dev, ino) が記録と一致したときだけ、中身を再帰的に消してから空のディレクトリを消す。symlink・ディレクトリでないもの・同一性の不一致は `FailedPrecondition` にして何も消さない。どの段でも `ENOENT` なら「既に無い」として成功扱いにする（冪等） |
| 失敗時の扱い | delete は `Ok` のまま（`Err` にしない。状態は既に消えている。エラーを返すと再実行が `NotFound` になる。`image_ref_release` と同じ考え方）。結果は `DeleteResponse::image_rootfs` に `Kept { code }` で載せ（次行）、操作名 `image_rootfs_remove` で `OpRecorder` にも記録し、木は残す |
| delete の後始末の結果の返し方（#2633・OCI-7・CRI-2・SUP-7・REPAIR-4・PLUG-1） | **`DeleteResponse` に載せる**。理由: (1) 記録器は件数の集計で、呼び出しごと・コンテナごとの結果を運べず、CLI は `OP_LOG_ENV` のときしか出さないため利用者は木が残ったことを知れなかった、(2) `ContainerRuntime` の実装は plugin 側（PLUG-1）で、RPC 境界の先の結果を呼び出しごとに返せるのは戻り値だけ。**delete の成否は変えない**（終了コード 0・CRI の `RemoveContainer` は成功のまま）。型は `CleanupOutcome`（`NotApplicable`〔既定〕・`Removed`・`AlreadyAbsent`・`Kept { code: ErrorCode }`。パス・errno は含めない）で、欄は `image_rootfs`・`supervisor_log`・`container_log`。埋める層: `image_rootfs` は core の delete（記録なし = `NotApplicable`、`Removed` / `NotPresent` = `Removed` / `AlreadyAbsent`、失敗 = `Kept { code }`）、`supervisor_log`・`container_log` はログを消す層（plugin-cri。`Finished` = `Removed`〔期限内に終えた best effort〕、`TimedOut` = `Kept { Timeout }`、失敗 = `Kept { code }`、状態ルートが無いストア = `NotApplicable`）。出し方: CLI は `image_rootfs` が `Kept` のとき stderr に 1 行 JSON（`code` + 固定文言 `image rootfs removal failed; leftover rootfs may remain`）の警告を出し、終了コードは 0（ログ側の警告は従来のまま）。CRI は cri-api の `RemoveContainerResponse` にフィールドが無い（無改変。CRI-3）ため応答には載せず、plugin-cri が `Kept` 1 件につき 1 行の構造化ログ（`event: container_delete_cleanup`・`id`・`target`・`code`）を `LineSink` 経由で stderr に出す。cri crate の `RuntimeDeleteResult` は同じ 3 欄を `RuntimeCleanupOutcome` に写す（未知の値は `Kept { Internal }`）。記録器への計上はメトリクスとして残す |
| 作成世代の照合（#2378） | (dev, ino) は rootfs を手で消して同名のディレクトリを作り直すと再利用されうる。そこで create は展開後・公開前に、rootfs 直下の印のファイル `.fandhe-container-rootfs-owner`（0400）へ 128 bit の乱数トークン（小文字 16 進 32 文字）を書き、同じ値を状態レコードの `imageRootfs.token` に記録する。delete は固定した rootfs の fd 直下の印をリンク非追従・通常ファイルのみで読み、記録と完全一致したときだけ消す。印の欠落・不一致・記録のトークン欠落（旧記録）は `FailedPrecondition` で何も消さない。展開済みの木に同名のファイルがあれば（イメージ由来の偽の印）create が拒否する。コンテナ内から rootfs の `/` に印のファイルが見える |
| delete と create・start の排他（#2378） | `StateStore::delete` が成功するとストアのロックは外れる。rootfs を持つコンテナの delete は、状態削除の前から rootfs の後始末の完了まで bundle の所有ロック（`BundleLock`。start と同じ `flock`）を保持する。通常の create・`create_with_image` の状態作成も同じロックを取り、保持中は `FailedPrecondition`（何も変えず再試行）。start は既存の `BundleLock` で排他される。create・delete のロックは bundle が指す実体に取る（祖先が symlink なら解決した実体の経路で取り直す。ロックは inode に掛かるため、表記の違う bundle 経由でも同じ実体なら排他する）。Linux でそれでもロックを取れない create は状態を作らずに拒否し、delete は状態を消すが rootfs は消さずに残して失敗を記録する（fail-closed）。Linux 以外はロックが未実装で、create は排他なしで進み、delete は rootfs を消さない |
| 同じ ID の再作成との競合 | 旧い最終名がある間は、新しい `create_with_image` は `RENAME_NOREPLACE` のため公開できない。同じ名前に別の同一性の実体があるのは差し替えられた場合だけで、そのときは消さない |
| 他コンテナとの共有 | core が所有する rootfs を、別のコンテナ（通常の create で同じ bundle を指す、別 bundle の絶対 `root.path` で指す）が使う構成は支援しない。その場合 delete が使用中の rootfs を消して壊れる（create 間の排他が無いため。#2353 の注記を引き継ぐ） |
| 公開済みで状態の無い rootfs の回収（#2540・決定 A） | 公開後・状態作成前のクラッシュ、delete の rootfs 削除の失敗、状態の喪失で残った木を、同じ bundle の次の展開器つき `create_with_image` が、展開先を作る前に回収する。次をすべて満たすときだけ消し、確かめられなければ残して従来どおり `AlreadyExists` にする: (1) bundle の所有ロック（`BundleLock`）を取れる（保持中は残す。delete・状態作成と排他）、(2) 最終の名前がリンクでないディレクトリで親と同じマウント、(3) 木への `flock` が取れる（`WouldBlock` は生きている create）かつロック中に開き直した実体が同じ、(4) 印が v2 以降の形式でリンク非追従・通常ファイル・nlink 1・所有者が実効 uid・mode 0400、印の (dev, ino) が木の実体と一致する、(4a) 印が v3 で、3 行目の状態ルートの識別子が現在のストアのものと一致する（不一致・v2・ストアが `host_state_root` を示せない場合は消さず、記録は失敗。#2635・決定 F）、(5) `StateStore::list` を全件（ページ数に上限）調べ、印のトークンを持つレコードも同じ bundle（文字列または追従して開いた (dev, ino) が同じ）を指すレコードも無い。一覧の失敗・打ち切りは残す。生きている create は、`CreatedRootfs` が状態作成の完了まで木の `flock` を保持することで見分ける。記録は操作名 `image_rootfs_orphan_reap`（回収した = 成功、使用中・確かめられない・失敗 = 失敗）。ロックは判定と削除の間だけ保持する（展開の全体では保持しない）。別の状態ルート（`--root` 違い）のコンテナが同じ bundle の rootfs を共有する構成は支援しない（決定 F で、core 製の木は消さずに残す） |
| 印の v2・v3 形式（#2540・#2635・決定 B） | 印は 1 行目 = トークン（小文字 16 進 32 文字）、2 行目 = 木の作成時の `<dev>:<ino>`（10 進）。`cp -a` で別の bundle へ複製した木は inode が新しく、2 行目が一致しないので孤児として消さない。delete は v1（トークンだけ）と v2 の両方を受ける（既存の記録との互換）。孤児の回収は v2 で同一性が一致するときだけ消す（v1 は残す）。v3（#2635）は 3 行目に状態ルートの識別子（`StateStore::host_state_root` の絶対パスのバイト列の SHA-256 の先頭 128 bit を小文字 16 進 32 文字にしたもの。生のパスは印に書かない。(dev, ino) でなくパスにしたのは、tmpfs の状態ルートが再起動で一致しなくなり正当な孤児の回収が退行するのを避けるため）を持つ。delete は v1・v2・v3 のすべてを受け（自分の状態ルートのレコード経由なので識別子の照合は要らない）、孤児の回収は v3 で識別子が一致するときだけ消す（v2 は別の状態ルートのものかもしれず確かめられないので残す。v2 は同じブートの tmpfs 由来に限られ影響は小さい）。印の長さは 108 バイト以下（上限 128）。印はコンテナからも `/` に見え、dev・ino と状態ルートのパスのハッシュが見える。再起動で `st_dev` が変わる状態ルートでは一致しないので残す（手動で回復する） |
| subuid 所有の木の削除（#2540・決定 C） | rootless で userns の中の展開器が作った木（`OwnershipPolicy::ChownInUserNamespace`）はホストの実効 uid では `chmod`・`read_dir`・`unlink` が `EPERM` になる。権限を `ImageRootfsPrivilege`（既定 `HostEffectiveIds`、`SubordinateIds(SubordinateIdSource)`）で宣言する: create は `ContainerImage::with_rootfs_privilege`（状態の `imageRootfs.ownership` に `subordinate` を記録）、delete は `DeleteOptions`（`delete_with_options`・`delete_releasing_image_ref_with_options`）、展開途中の回収は `ReapOptions`（`reap_stale_unpacks_with`）。`SubordinateIds` のときは、子プロセスの User namespace（コンテナ 0 → 自 euid、1.. → subuid 範囲。`newuidmap` 経由の既存の holder / mapper 方式。Mount ns は分けず `mnt_id` の照合を保つ）の中で、固定済みの親の fd・(dev, ino)・所有者照合を継承して同じ削除を行い（経路を再解決しない）、固定の終了コードで結果を返す。親は期限つきで待ち、超えたら kill して回収する。呼び出しがマルチスレッドなら fork の検査で `FailedPrecondition` となり木を残す。適用先は delete・create 失敗の後始末・展開途中の回収・公開済みの孤児の回収の 4 経路。記録が subordinate なのに権限が無い delete は、木に触れず `FailedPrecondition` を `image_rootfs_remove` の失敗として記録して残す（ホストで試して `EPERM` のときだけ userns で再試行する方式は、部分削除の順序依存を避けるため採らない）。`imageRootfs.ownership` の不明な値は破損として拒否する。削除は印を最後に消すので、途中で失敗・期限切れになっても印が残り、次の孤児の回収が木を見分けられる |
| 展開途中の木の判定と観測（#2540・決定 D） | 展開途中の木（`.fandhe-unpack-*`。節「展開途中の木の回収」）の回収条件から mode 0700 の要求を外す。証拠は予約名・リンクでないディレクトリ・所有者・ロックが取れること・ロック中の同一性の再確認で、mode ではない（userns の展開器はイメージの `./` の項目で展開先 root の mode を変えうる）。所有者は実効 uid、権限が `SubordinateIds` なら subuid の範囲も受ける。rootful でイメージが所有者を 0 以外へ変えうるのは展開先の子だけで、判定するラッパーは実効 uid 所有のまま回収できる（節「展開途中の木の回収」。#2635）。この変更より前の平らな構造の木で所有者が変わったものは `Unverified(Owner)` で残す。残した理由は `StagingReclamation::kept_unverified_reasons`（`UnverifiedReason`）で見え、`reap_stale_unpacks_with` と create は `image_rootfs_reap_kept_unverified`・`image_rootfs_reap_failed`・`image_rootfs_reap_truncated`・`image_rootfs_reap_scan_failed` を 1 件ずつ失敗として記録する（`OpRecorder::snapshot` の失敗数が件数になる） |
| 状態ルート全体の掃引はしない（#2540・#2635・決定 E。確定） | 孤児は状態レコードを持たないので `StateStore::list` でも参照テーブルでも bundle を列挙できず、状態ルート全体を掃引するには create の開始時に bundle を残す意図の記録（journal）が要る。journal を入れても、それを読んで掃引する契機が無い: 候補は「起動時の全件照合」と「新しいトップレベルコマンド」だけで、どちらも `container-ref-reconcile.md` の決定 2 で不採用（CORE-1: 常駐デーモンが無く CLI に「起動時」が無い、CLI の表面と 3 OS の parity〔CLI-1〕への波及）。加えて journal 自身の寿命（書き込み・後始末・クラッシュ時の整合）、状態ルートの既定が tmpfs で再起動で消えること、状態ルートという信頼境界（OCI-5）に新しいファイル形式が増えることの重さがある。孤児が実害（同じ bundle の create が `AlreadyExists` で止まる）を出すのは同じ bundle を再び使うときだけで、その契機では既に回収している。よって journal を入れない。契機は (1) 同じ bundle への次の `create_with_image`（展開途中の木と公開済みの孤児の両方）、(2) bundle を知る呼び出し元が呼ぶ `reap_stale_unpacks` / `reap_stale_unpacks_with`（展開途中の木）の 2 つに限る。運用者が孤児を見つけて消す手段は節「失敗後の手動回復」 |
| 展開先のラッパー構造（#2635・決定 G） | 展開先を 2 段にする: core 専有のラッパー `.fandhe-unpack-<pid>-<seq>/`（0700・実効 uid 所有。展開器へは渡さない）と、その子 `rootfs/`（展開器へ `/proc/self/fd/N` で渡す実際の展開先）。イメージが所有者や mode を変えられるのは子だけなので、回収が判定する予約名のラッパーは実効 uid 所有のまま回収できる（rootful で `./` の項目が所有者を 0 以外へ変えても `Unverified(Owner)` にならない）。判定の条件（予約名・リンクでないディレクトリ・所有者・`flock`・ロック中の同一性の再確認）は変えず、予約名の位置に他人が置いたディレクトリは所有者の照合で落ちる。bundle の親に書ける者は、rootful では bundle の設定自体を握る信頼された主体で、この前提は従来と同じ。公開は子をラッパーから最終の名前へ `renameat2(RENAME_NOREPLACE)` で移し（別ディレクトリへの改名は移すディレクトリ自身の write 権限が要るため、展開器が 0555 等にしていれば固定した fd 経由で一時的に補って戻す）、空のラッパーは best effort で消す（消し損ねても次の回収が拾う）。ラッパーの名前が予約名なので `root.path` から子へは到達できない。この変更より前の平らな構造の木は従来の挙動のまま残る。子の最上位が subuid 所有で他者書き込み不可のとき（rootless でイメージの `./` が root 以外の所有）は、ホストの実効 uid では mode の補完も別ディレクトリへの改名もできないため、権限が `SubordinateIds` なら印の書き込み（seal）と最終の名前への改名（publish）を子プロセスの user namespace の中で行う（#2690。子は固定済みの fd と固定の 2 つの名前だけに触れ、経路を再解決しない。印はホストの実効 uid 所有・0400 で作られる。公開済みかは子の終了コードではなく、最終の名前が展開した実体〔dev・ino〕を指すかの観測で決めるので、期限切れで kill しても改名が済んでいれば公開済みの木を消さない。期限は写像の書き込みの期限に `USERNS_FINALIZE_BUDGET`〔30 秒〕を足したもの）。権限が `HostEffectiveIds` のときは暗黙に userns へ昇格せず、明示エラー `failed to publish rootfs: cannot make unpacked root writable for rename (owned by another uid)` で拒否する（seal の失敗も同じ文言）。呼び出し元がマルチスレッドなら fork の検査で `FailedPrecondition` になる（子プロセス方式の配線は #2315 の範囲）。残る制限: 最上位が subuid 所有・他者の search 権限なし（0700）のまま公開された木は、公開後・状態作成前のクラッシュ時に孤児の回収がホストから印を開けず `Unverified` で残り、次の create は `AlreadyExists` で止まる（0555 等で他者に r-x があれば従来どおり回収できる） |
| 別の状態ルートとの共有（#2635・決定 F） | 検出できる構成: 状態ルート A の `create_with_image` が作った公開済みの木を、状態ルート B の `create_with_image` が孤児と取り違える。B の `StateStore::list` に A のレコードは見えないが、印 v3 の識別子（A のパスのハッシュ）が B のものと一致しないので、B は消さず `AlreadyExists` で拒否する（記録は `image_rootfs_orphan_reap` の失敗）。v2 の印・識別子を示せないストアも同様に残す（fail-closed）。検出できない構成: 状態ルート B の通常の `create` が、A の core 製の木を `root.path` で採用した構成（B のレコードは A から見えない）。A の delete がその木を消すが、検出できず支援しない。通常の create が core 製の木の採用を拒否する案は同じ状態ルートの挙動も変えるため入れていない（後続の候補）。状態ルートのパスの表記が変わる（symlink 経由・移設）と識別子が変わり別の状態ルート扱いになる（残す側に倒れる） |
| Linux 以外 | 展開の作成が `Unimplemented` なので記録は生じない。記録が現れても経路を再解決して消さず、`Unimplemented` で拒否して失敗として記録する |

## 前提・制約

- 既定の削除は展開と同じ実効 ID で走る。rootless の userns 内での展開が作る subuid 所有の木は、`ImageRootfsPrivilege::SubordinateIds` を渡したときだけ userns の中で消せる（決定 C）。CLI / CRI / supervisor からの権限の受け渡しは #2315・#2243 の配線の範囲で未実装（REPAIR-3）。マルチスレッドの呼び出し元（CRI の tokio 等）は fork の検査で拒否されるため、子プロセス方式の配線が別途要る
- 状態ルートの既定は tmpfs（`/run`・`$XDG_RUNTIME_DIR`）なので、記録は同じブート内のもの。`--root` で永続ストレージを使い再起動を挟むと、`st_dev` が変わるファイルシステムでは同一性が不一致になり、消さずに残す（安全側）
- 件数（100 万）と深さ（256）の上限を超える木は、消し切らずに失敗として記録して残す（無限にかからない。REPAIR-5）
- 所有者 uid の照合はしない。rootful では展開が root ディレクトリの所有者を image の値へ変えうるため、同一性は (dev, ino) で判定する
- 記録は `state.json` の `imageRootfs` に書く。キーの無い既存ファイルは「記録なし」として読み、値が検証（相対・Normal 要素のみ・予約名なし・4096 バイト以下）に通らなければ破損として拒否する（状態ルートは信頼境界。OCI-5）

## 展開途中の木の回収（#2379・OCI-7）

展開先は 2 段（ラッパーと子。決定 G・#2635）で、以下で「木」と呼ぶ判定の対象は予約名のラッパーである。展開の途中でプロセスが落ちると、非公開の名前 `.fandhe-unpack-<pid>-<seq>` の木が残る。持ち主がいるかは PID ではなく、木のディレクトリへの OS ロック（`flock`）で判定する。作る側は作った直後に排他ロックを取り `CreatedRootfs` が生きている間保持する（プロセスが落ちれば OS が外す）。回収する側は固定した親の fd の下で予約名（`^\.fandhe-unpack-[0-9]{1,10}-[0-9]{1,20}$`）の兄弟を調べ、リンクでないディレクトリ・所有者が実効 uid（権限が `SubordinateIds` なら subuid の範囲も）・ロックが取れる・ロック保持中に開き直した実体が同じ（dev・ino）ものだけを消す。どれかを確かめられなければ残す。走査数（4096）・件数・深さに上限を置き、ロックは `try_lock` だけで待たない。契機は同じ bundle への次の create と `reap_stale_unpacks`（`_with` つきは記録も行う）に限り、状態ルート全体の掃引はしない（決定 E）。

## 失敗後の手動回復

公開済みで状態の無い木は、上の決定 A の条件を満たせば次の `create_with_image` が自動で回収する。回収されずに `AlreadyExists` で止まり続けるとき（`image_rootfs_orphan_reap` の失敗、印が v1・v2・複製・欠落、別の状態ルートの使用、状態ルートのパスの表記が変わった、再起動で `st_dev` が変わった等）は、運用者が次の手順で孤児を見つけて消す。

観測の現状: `OpRecorder` の計数（`image_rootfs_orphan_reap`・`image_rootfs_reap_kept_unverified` 等）は計測の差し込み口で、CLI から表に出ていない。運用者はファイルシステムで次のとおり確かめる（計測を表に出す手段は別の課題）。

1. 公開済みの core 製の木を探す: `find <bundle の置き場> -xdev -name .fandhe-container-rootfs-owner -type f`（印は木の直下にある）
2. 印の 1 行目（トークン）を、使っている状態ルートごとに照合する: `grep -l '"token":"<トークン>"' <状態ルート>/*/state.json`（レイアウトは `<id>/state.json` の `imageRootfs.token`）。印の 3 行目は状態ルートの識別子で、`printf '%s' <状態ルートの絶対パス> | sha256sum | cut -c1-32` で求められる。どの状態ルートの `state.json` にも参照が無く、同じ bundle を指すレコードも無ければ孤児の候補
3. 展開途中の木（`<bundle>/.fandhe-unpack-*`）は、`flock -n <dir> true` が成功しても、その場でロックが外れるため使用中でないことの保証にならない（確認の後に create が同じ木のロックを取って展開を始めうる）。手順の前提として、対象 bundle に関わる create・delete のプロセスを止めておく。そのうえで削除までロックを保持する: `flock -n <dir> rm -rf --one-file-system <dir>`（ロックを取れなければ何も消さない。取れた後に `<dir>` が確認した実体〔`stat -c '%d:%i'`〕のままかを手順 4 の前に照合する）
4. 削除: rootful は `rm -rf --one-file-system <dir>`。subuid 所有の木は `podman unshare` 相当の userns の中で消す。`image_rootfs_remove` の失敗が subordinate の木だったときは、delete が状態の削除まで済ませており delete し直しは冒頭の状態取得で `NotFound` になるため使えない。権限（`SubordinateIds`）つきの次の create（`ContainerImage::with_rootfs_privilege`）による孤児の回収に任せることもできる

delete の rootfs 削除の失敗は `DeleteResponse` の `image_rootfs`（`CleanupOutcome`。#2633）に載り、CLI が警告 `image rootfs removal failed` として表に出す。plugin-cri では `container_delete_cleanup`（`target: image_rootfs`）が手動回復のきっかけになる。

## 対象外（後続の候補）

- CLI / CRI / supervisor から `ImageRootfsPrivilege`・`DeleteOptions`・`ReapOptions` を渡す配線（#2315・#2243）と、マルチスレッド経路の子プロセス方式
- 通常の `create` が core 製の木（同一性が一致する v2 / v3 の印を持つ木）を `root.path` で採用するのを拒否すること（同じ / 別の状態ルート。検出できないまま残る構成。決定 F）
- `OpRecorder` の計数（`image_rootfs_orphan_reap` 等）を運用者へ出す手段
- 最上位が subuid 所有・0700 のまま公開された木の、公開後・状態作成前のクラッシュからの孤児の回収（印の読み取りを `SubordinateIds` のとき userns の中で行う案。決定 G の残る制限。#2690 の後続候補）
- rootful でイメージが所有者を変える場合の実機確認（root 版。#1621 の範囲。CI の rootless 試験は子の所有者を subuid へ変える代役で確かめる）
- rootful でイメージが所有者を 0 以外へ変えた展開途中の木の自動回収（`Unverified` として観測できるだけ）
- イメージ参照の解除（`image_ref_release`）の結果を `DeleteResponse` に載せること（現状は記録器のみ。安全側で、起動時の照合 #854 が回収する）
- plugin RPC（#1869 の `RuntimeResponse::Deleted`）の DTO へ後始末の欄を足すこと（RPC の実装時に行う。plugin から受けた値は untrusted として閉じた語彙へ写す）
- 参照と blob の起動時照合（#854）が rootfs の木を GC・prune の対象にするか
